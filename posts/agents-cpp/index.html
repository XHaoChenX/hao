代码仓库分析工具 Agents 蜂群

May 19, 2026 · HaoChen

背景#

因为很多人都会去思考如何高效分析代码仓库问题, 其实我之前并没有认真想过这个问题.

设计思路#

把一个代码仓库分析任务让一个分析agents进行拆解, 然后通过agents子蜂群(我叫它蜂群, 因为很像一堆小蜜蜂)去并发的完成这些子任务, 最后再汇总后让架构agent去完成架构图绘画.

这个想法一直有却没有实现过, 多子agents并行, 自然就联想到并发方式去实现了, 可惜我这kimi送的免费10块钱好像只支持3并发(个人强迫症要用完,所以你发现我很多项目都用kimi,只是因为这10块钱没用完,当然我写的ai工具都设计过KV cache命中和优化精简prompt,所以这10块钱异常持久..当然我只是用它做测试用, 写代码这个项目用的claude code + dsV4flash), 为了解决这个并发限制, 自然又要引入线程池来限制它每次并发请求次数.

这个项目几乎从零实现, 仅依赖一个 C++ JSON 第三方库, 连 API 请求都是直接通过 HTTP 完成的。另外我自己封装了一套 Dabai Agents, 其架构图可去我的 GitHub 查看

效果展示#

具体实现可以直接看它自己生成的架构图, 没错我创造了它, 它分析了自己并且画出了自己的架构图.

心得#

随着项目的复杂, 和长期使用ai coding 其实大部分人都有逐渐领悟出自己一套高效ai coding的方法.

大模型本质对我来说也是一个工具, 人之所以和普通动物不一样是因为人会用工具, 但是不同工具在不同人手里是不一样的, 它也是需要熟练度的, 熟练度可以弥补模型些许不足, 提高驾驭模型能力就能提高生成代码质量, 当然控制变量模型能力相同情况下.

它的作用对我来说, 就是不用我去做那些很详细的实现, 但是这不意味着我不用去看ai 生成的实现, 正如安德烈·卡帕西说, 你可以外包你的思考, 但不能外包你的理解。如果你还不能理解这句话, 说明都还不真正懂ai coding.

你可以让ai和你讨论方案, 让它帮助你实现, 但是你不能不理解这个过程。因为如果你不能理解它生成的代码, 并且在脑海里形成整个代码架构图并且带领着它完成你的实现, 那么你就无法真正维护住这个项目。总会有一天项目复杂到脱离你的掌控.

对 Agents 的看法#

写多了agents, 我得出一个结论: 大模型还是适合做分析, 不适合做执行

如果要做执行, 最好还是把执行相关流程写成脚本或者代码。最差也得走function call/tools方式。不要直接user prompt 添加限制让模型返回.

skills方式其实底层多套了层function call, 对于大模型来说, 你每创造一次tools判断就会导致多一层幻觉。对于通用agents工具确实很好用。但是对于业务固定或者说工作流固定的pipeline并不适合.
